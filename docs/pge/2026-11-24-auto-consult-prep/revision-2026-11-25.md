# Revision, Nov 25: one full brief, one source (PLAN; no build until Taylor OKs)

What happened: for a Nov 25 consult, Rebecca received lawmatics-mcp's pre-consult brief as the facts-card fallback.
- It said "AI brief unavailable: not configured", because `ANTHROPIC_API_KEY` is unset on that project.
- It printed the referral source as a raw Lawmatics picklist id.

Taylor: "no it should have all the info from the prep we drafted today."

This also corrects the Nov 24 premise that Rebecca was getting no briefs at all. lawmatics-mcp IS sending them; they are just the thin version.

State of Lectual today: S1 is on main. It is NOT emailing anyone, because `CONSULT_PREP_FROM` is unset and the assistant is not switched on. So there is no duplicate risk from Lectual yet.

## Requirements (from the director, Taylor's words)
1. The brief Rebecca gets automatically is the FULL prep: facts, intake/form answers, USPTO knockout, class and risk read, package, and questions. It is never the facts card when a full prep exists.
2. A prep already drafted for that lead or consult (the same day, or since the booking) is REUSED. It is not regenerated, and no second, thinner email is sent.
3. There is ONE brief source. The other stands down, and the duplicate risk on switch-over day is stated.
4. Lawmatics picklist values print as their LABELS (referral source and every other select field), wherever a brief prints them.

## Decisions proposed

**A. Lectual owns the brief. lawmatics-mcp stands down.**
- Lectual is multi-firm, uses each firm's own Lawmatics token, and already holds the trigger, the markers, the cancel-on-change logic and the lead-page card.
- lawmatics-mcp serves one firm only and runs on a deployment-wide token, which the rules forbid for a firm feature.
- lawmatics-mcp stands down with `CONSULT_PREP_ENABLED=false` on its Vercel project. Its other jobs (the morning brief, the 8 PM recap) keep running.
- Rejected: lawmatics-mcp reading Lectual's stored prep. It would keep two send engines and two clocks, and it is single-firm.

**B. Lectual emails only a full brief (S2 must ship before any Lectual email).**
- S1's facts brief stays as what the lead-page card shows while a full brief is being built. It is never emailed when a full brief exists.
- S2 ports the judgment half of lawmatics-mcp's `src/consult-brief/` into Lectual, per firm:
  - USPTO knockout;
  - class and risk read;
  - package recommendation from the firm's own list (prices never from the model);
  - questions;
  - the packages PDF and the USPTO CSV, attached to the email and saved to the lead's Documents & files (Taylor approved Nov 24).
- **Model:** Sonnet, per this repo's no-Opus rule. lawmatics-mcp used Opus. Recommendation: use Sonnet, compare the first week's briefs, and change only if Rebecca finds them weaker.
- **If the full build fails** (model error, USPTO down): the run retries on the next sweep, and the 24h email waits for it.
  Open question Q1 is what happens at the 1-hour mark if there is still no full brief.

**C. One stored prep per consult, reused.**
- The prep is built ONCE per consult key and stored: the internal BRIEFING item in Approvals, the marker, and the files.
- Every email (booked, 24h, 1h) is that SAME stored brief. Nothing is regenerated per send.
- Re-run is the only way to make a new one: a person's choice, and it sends only a fresh booked email.
- **A prep drafted by a person or a skill is also reused.**
  - Before building, Lectual looks for a BRIEFING already in Approvals for that lead, created since the booking or today. It is linked to the lead by the queue's own `resolveBatch` rules, and must come from `prep-consult` or `consult-prep`.
  - If found, Lectual adopts it: it marks the prep with that item's id and emails ITS text, and builds nothing new.
  - It is only reused when it is a full brief (it has the class/risk/package sections). A heads-up-only item is not reused as the full brief.
  - Open question Q2: where "the prep we drafted today" actually lives.

**D. Picklist labels.**
- Lectual's Lawmatics read already asks `/custom_fields` for field names (`lead-origin-read.ts`).
- S2 widens that one read to also keep each select field's options (id to label), once per run. The brief prints:
  - the `formatted_value` when Lawmatics gives one;
  - else the option label;
  - else "not recorded".
- A raw number is never printed. Referral source uses `leadOriginFromProspect`, which already prefers `formatted_value`.
- The same fix is needed in lawmatics-mcp's `facts.ts` ONLY if it keeps sending during the interim (see E).

**E. Switch-over and duplicate risk.**
- **The risk:** lawmatics-mcp hands each brief to Resend with `scheduled_at` up to about 24 to 48 hours ahead, and it never cancels.
  - Setting `CONSULT_PREP_ENABLED=false` stops NEW schedules only.
  - Every 24h and 1h brief lawmatics-mcp already scheduled for consults in the next 1 to 2 days will still go out.
  - Those emails come from rpblawfirm.com's Resend account, whose key Lectual does not hold, so Lectual cannot cancel them.
- **The fix:** a cutover time, `CONSULT_PREP_CUTOVER_AT`, set on Lectual when lawmatics-mcp is switched off.
  - For a consult that starts within 48 h of the cutover, Lectual sends NO 24h or 1h email, because lawmatics-mcp already has.
  - Lectual still builds the full brief, shows it on the lead page, and sends the booked email only if lawmatics-mcp would not have sent anything.
- **Residual risk on switch-over day:** Rebecca may get lawmatics-mcp's (thin) version for consults in the first 48 h, rather than two emails. Nothing doubles.
- **Interim, until S2 ships** (Q3): setting `ANTHROPIC_API_KEY` on lawmatics-mcp makes its briefs full again tomorrow, with no code change. Doing so is a production setting, so it needs Taylor's OK.

**F. The sender (unchanged open item).** `CONSULT_PREP_FROM` is held until we know which Resend account Lectual's `RESEND_API_KEY` belongs to.
